Data foundation
Scorecard

Data quality scorecard

analysis/data-quality-audit/output/quality_rubric.md

Six standard quality dimensions run against the real dataset (3,200 customers, 8,868 funnel events, 7,949 email engagements, 474 reviews, plus the 669-row raw CRM export): Completeness 9/10, Accuracy 10/10, Consistency 10/10, Uniqueness 8/10, Validity 10/10, weighted overall 9.41/10, zero Critical or High findings. Timeliness is marked N/A rather than forced into a misleading number, since this is a static generated dataset, not a live pipeline with an SLA.

The one Uniqueness deduction is deliberate, not a defect: company_name reads 76% null overall, but that's exactly segment mix (100% populated for trade/commercial, 100% null for homeowner/designer), not a gap. A generic outlier check also flags 311 of 1,654 amount values (18.8%) as IQR outliers, all 311 from the trade/commercial segments even though those two segments are only 19.4% of purchases, the expected shape of mixing very different order sizes, not a data-entry problem.

One real engineering note: the vendored null_counter.py script crashes under Python 3.14 (an argparse bug tripping on a bare % in a help string), worked around by importing its core function directly rather than patching the vendored file.

EDA notes

EDA structural notes

analysis/data-quality-audit/output/eda_findings_summary.md

Three structural findings, none of them quality defects. funnel_events.amount is 81.4% null because only purchase and repeat_purchase events carry a dollar value, so any blended AOV stat across all customers without a segment cut is misleading. sku_collection is 37.8% null, flagged as worth a follow-up cut by event type before trusting it in collection-level analysis. correlation_explorer.py genuinely doesn't apply to this schema, since every table has at most one numeric measure column.

What looks good: referential integrity is 100% clean across all three child-to-parent relationships (17,291 combined rows, 0 orphans), customer_id is 100% unique everywhere including the intentionally messy raw CRM export, and all three business-rule checks pass with zero violations. Verdict: data is ready for analysis, no fix required before proceeding.

Definitions

Semantic model

analysis/semantic-model/README.md

Every funnel metric this project reports, formalized into YAML following dbt Semantic Layer conventions: 6 funnel-stage metrics, 4 dimensions, and the core entities and relationships, validating cleanly against a strict schema validator. It documents real gotchas already hit the hard way elsewhere in this project rather than a clean textbook definition: project_rate's denominator must be filtered to trade/commercial only, since homeowner and designer customers never trigger a project_upload event at all. repeat_purchase_rate documents the cohort-anchoring mistake the cohort analysis made and fixed: anchoring cohorts on signup date produces nonsensical rates above 100%, first-purchase-date is the correct anchor.

Nothing in the schema's structure is Fireclay-specific; swapping the data-source and expression fields adapts it to a different business unchanged.

CRM reconciliation
Finding

HubSpot ↔ Salesforce: the findings

analysis/crm-reconciliation/output/reconciliation_findings.md

Both inputs are live API extracts, not fixtures: 188 HubSpot records, 385 Salesforce records. The matcher found 92 matches total (85 by exact email, 7 by fuzzy name+company), 96 HubSpot-only orphans, 293 Salesforce-only orphans. The 7 fuzzy matches are investigated openly rather than hidden: all 7 are false positives, genuinely different people who happen to share a surname or a repeated company-name template, about 1.7% of 403 candidate pairs, a real limitation of name/company matching without a third identifying field.

The real finding, isolated to the 85 genuine cross-system matches: 100% show a lifecycle-stage mismatch, one mechanism every time, not scattered noise. HubSpot's lifecyclestage reads "lead" while Salesforce's Lead.Status reads "Closed - Converted," because the original HubSpot import set five custom properties but never touched HubSpot's own standard lifecycle field. A secondary drift: 25 of the 85 pairs (29%) show Salesforce's company name as HubSpot's value with an " Inc" suffix appended, consistent with sales-side normalization on lead entry.

Systems memo

HubSpot ↔ Salesforce: the systems memo

analysis/crm-reconciliation/systems-requirements-memo.md

Answers the JD's "systems requirements needed for better growth decisions" line literally. The fix is narrow because the failure is narrow: a native Salesforce Flow firing on Lead.Status transitioning to "Working - Contacted" or "Closed - Converted," calling HubSpot's Contacts API to set lifecyclestage on the matching contact, joined on email. The mapping: "Working - Contacted" to salesqualifiedlead, "Closed - Converted" to customer, one-directional by design since Salesforce becomes the system of record once a lead is actively worked.

Explicitly argues against a platform purchase (Zapier, Workato, a native connector): those solve problems this data doesn't show exist yet. Rollout note: backfill the 85 already-mismatched contacts once before turning the Flow on, or the fix only stops new drift and this round's findings stay permanently stale.

Methodology

HubSpot ↔ Salesforce: the reusable tool

analysis/crm-reconciliation/README.md

reconcile.py is a pure function (two record lists plus a parsed config in, a match/orphan/mismatch report out) with zero hardcoded Fireclay field names anywhere in its matching logic, every field name comes from config.yaml at call time. Matching runs exact email first, then falls back to fuzzy name+company for whatever's left unmatched on both sides.

One honest caveat documented rather than glossed over: the reusable REST-based HubSpot extractor script was written but never actually executed in this project, since the live HubSpot data was pulled directly through Claude Code's MCP connector in the same build session instead. Known limitation, stated plainly: fuzzy matching without a third identifying field will occasionally produce false positives (this project's own run: 7 of 403 candidate pairs, 1.7%).

Experimentation
Finding

Experimentation: the feasibility check

analysis/experimentation/feasibility_findings.md

The backlog's Hypothesis 1: a trade-show second-sample nudge, tested as a 90-day holdout-vs-treatment, scaling at an 8-point lift in second-sample rate. Real historical volume: 198 trade-show trade customers over 20 months, 10.05 leads per month. A standard two-proportion power calculation (α=0.05, 80% power) against an 11% baseline needs 623 total leads to detect an 8-point lift, meaning 62 months, over 5 years, to reach that number at current volume.

Checked whether measuring a faster-arriving proxy (email click-through, real rate 17.6%) would fix the timeline. It doesn't: even a full 2-year wait can only reliably catch a 13.8-point improvement, on either metric, nearly double the original 8-point threshold. The constraint is population size, not metric choice.

Decision memo

Experimentation: the decision memo

analysis/experimentation/decision_memo.md

Answers the JD's "scale, stop, or learn next" language directly with a stop-and-learn on the test design, not the hypothesis. Recommendation: skip the holdout, roll the nudge out to 100% of eligible single-sample trade-show leads, then track the second-sample rate directionally against the pre-rollout 11% baseline over two full quarters. This can't produce a trustworthy p-value at this N, stated plainly rather than dressed up. An explicit reversal bar is set: end the rollout if the rate isn't at least 5 points above baseline after two quarters.

Worth naming directly: an earlier draft planned to simulate a treatment effect and "run" the test against a synthetic cohort to produce a scale/iterate/kill result. That was dropped on purpose, a fabricated outcome would have been a more impressive-looking deliverable and a dishonest one.

Attribution
Finding

Attribution: platform metric vs. commercial outcome

analysis/lifecycle-attribution/output/attribution_findings.md

Six real email programs compared on platform metric (open/click rate) against commercial outcome (mean purchase value, engaged vs. unengaged), at three attribution windows. welcome is the one program where the conclusion flips by window: a 30-day look shows a −$56 engaged-vs-unengaged gap; a 90-day look shows +$242. Since tile is a considered purchase, a 30-day report on this program alone would have reached the wrong conclusion.

sample_followup and project_nurture show a negative value gap at every window tested, most plausibly a selection effect rather than the email causing lower spend, stated as a correlation, not causal proof. Most stark: reactivation and trade_engagement's 977 combined recipients show zero purchase or repeat-purchase events at any window, regardless of engagement, meaning open rate on those two programs is disconnected from any outcome this dataset can observe at all.

Methodology

Attribution: how the engine works

analysis/lifecycle-attribution/README.md

attribution.py is three pure, generic functions with no Fireclay-specific field names. It is explicitly not a causal-inference tool: it reports correlational gaps between engaged and unengaged recipients, never a randomized result, and treats every negative gap as a hypothesis for a designed test, not a decision on its own. Fully tested (6/6 passing) before being run against real data.

Retention & trend
Finding

Cohort analysis: repeat-purchase retention

analysis/cohort-analysis/output/cohort_findings.md

The first version of this analysis anchored cohorts on signup date and produced nonsensical retention rates above 100% in some cells, because tile is a considered purchase and almost no customer's first purchase happens in their signup month. Re-anchoring on each customer's first-purchase month instead fixed it, and that correction is documented rather than silently patched over.

The real result: only 15.4% of first-time purchasers (221 of 1,433) ever make a second purchase within the ~22-month window, and zero repeat purchases happen in month 1, across every one of the 20 cohorts old enough to observe it. Segment breakdown: trade repeat-purchases at 23.6%, designer 19.9%, commercial 18.1%, homeowner 10.8%, roughly double the homeowner rate for trade and designer. These segment counts independently reproduce a table already published elsewhere in this project, a second cross-check that this project's headline numbers hold up under a different computation method.

Finding

Time series: is the stall rate improving?

analysis/time-series/output/ts_findings.md

20 monthly points, 2024-01 through 2025-08. Trend: downward, a linear fit of −0.77%/month, weighted stall rate falling from 74.2% in 2024 to 71.7% through August 2025. The full-period time-weighted mean (73.97%) independently reproduces the already-published 73% headline stat. The most recent three months are the lowest sustained stretch in the series: 62.5%, 60.0%, 57.1%.

One statistically flagged anomaly, November 2024 at 25.0%, is explained plainly rather than treated as a real event: that month had only 4 leads total, so a single lead's outcome moves the rate by 25 points. The honest read: the improvement is real and worth monitoring, but at 4–11 leads a month it's too early to credit any specific cause.

Methodology

Time series: how it was built

analysis/time-series/README.md

A real bug, found and worked around rather than patched: the vendored analyzer script's __main__ block unconditionally calls a demo function and ignores sys.argv entirely, so its real --csv argument parsing is dead code. The fix was to import and call the underlying functions directly, bypassing the broken entry point, and to document the bug rather than editing the vendored file in place. The known limitation is stated plainly: 20 monthly points at low volume is thin for trend or anomaly detection, and every conclusion is stated as directional rather than confident as a result.

Root cause
False start, then honest conclusion

Root cause: chasing the improvement

analysis/root-cause/output/rca_findings.md

A structured hypothesis rule-out for the 2024→2025 stall-rate improvement. A generic drill-down tool's raw-count comparison flagged one SKU collection, Original Ceramic, as the "top driver," since it had the largest absolute count change. Re-checked as a rate rather than a raw count, that claim doesn't hold: Original Ceramic's stall rate did fall (88.9% to 64.3%), but Natural Press's rate rose (56.2% to 69.2%) and Thin Brick's rate also rose (64.3% to 81.8%) over the same window. A real driver should move consistently in one direction; this doesn't.

Two hypotheses that could plausibly explain a real improvement, sales rep performance and inventory availability, aren't testable at all: no rep field exists anywhere in the dataset, and only current-state inventory is modeled. Final verdict: inconclusive, most consistent with a diffuse, population-level drift, with two concrete systems-requirements gaps named for any future investigation.

Methodology

Root cause: how it was built

analysis/root-cause/README.md

Uses the vendored drill-down skill's functions, called directly after finding the same dead-CLI-entry-point bug already documented in the time-series skill, worked around the same way. The write-up's real contribution isn't the tool's raw output, it's declining to stop at the tool's own "top driver" claim and re-checking it as a rate before accepting or rejecting it. A structured process that ends in "no smoking gun, and here's exactly why" is treated as a real result here, not a failed analysis.

Business & dashboard
Finding

Business metrics: conversion rate is not revenue

analysis/business-metrics/output/ecommerce_metrics_findings.md

Designer converts at 60.7% (highest of any segment, nearly double homeowner's 43.4%) but generates $791 revenue per customer, second-lowest of the four segments. Trade converts at 34.2%, roughly half designer's rate, but generates $5,782 per customer, over 7x designer's, driven almost entirely by AOV: a trade order averages $13,670 against designer's $1,086. Commercial and trade have nearly identical AOV and revenue-per-customer despite trade having 2.5x as many customers, a smaller but equally high-value segment.

The explicit takeaway: a dashboard reporting conversion rate alone would rank designer as the strongest segment and trade as one of the weakest; a dashboard reporting revenue would show the opposite for trade. Homeowner is the largest segment by count (1,769, 55% of all customers) but smallest by revenue per customer ($526), high volume, low unit value.

Build note

Business metrics: built new, not force-fit

analysis/business-metrics/README.md

The vendored business-metrics skill's own documentation claims e-commerce coverage, but its actual shipped script's CLI only has SaaS flags (MRR, ARPU, churn, CAC, LTV), no AOV or GMV path exists at all. Rather than bend real purchase data into a subscription shape to force-fit the vendored tool, ecommerce_metrics.py is small, original, tested code: one function taking plain customer/order dicts with no Fireclay-specific field names, tested against AOV correctness, segment independence, and edge cases (4/4 passing).

Dashboard specification

analysis/dashboard-spec/output/dashboard_spec.md

A full two-page dashboard requirements spec, deliberately a document, not a built dashboard, since standing up a real BigQuery/Tableau/dbt stack for a synthetic dataset with no live pipeline behind it would be theater, not evidence. Every metric in it traces to a specific already-computed analysis in this project. Reactivation & AI workflow
Live systems check, tested and fixed

Reactivation: the mechanism, made real

docs/reactivation-flow.md

Rather than invent a completion rate no real customer produced, this round tested whether the Sample Kit Builder's reactivation mechanism actually works end to end against the live store. It didn't, until a real bug was found. Querying the three companion products' real Shopify inventory state found all three set to deny-oversell with 0 units on hand, an oversight from product creation, not a business choice. That combination means Shopify's real /cart/add.js rejects the add outright, the reactivation prompt would have failed silently the exact moment a real trade lead clicked it, with no error anywhere a merchandising owner would notice.

Fixed live: all three SKUs restocked to 25 units, confirmed via each API call's response payload, not assumed. Fixed in code: the button now resolves real variant IDs server-side in Liquid and posts an actual /cart/add.js call, with honest success/error states replacing the original stub. Stated plainly: the easier write-up would have been "confirmed the flow works," true of the design, false of the system as it stood.

Claude Code skill

Lifecycle Pulse: how it works

.claude/skills/lifecycle-pulse/README.md

A git-committed skill generating a week-over-week funnel digest (interest, sample, project, purchase, repeat, advocacy) by segment, with anomaly flags on threshold-crossing declines and an optional live HubSpot/Salesforce cross-reference. The digest logic and snapshot builder are real, tested code; three of four snapshot dates are backdated re-derivations built to prove the delta logic without waiting three real weeks; one digest run is genuinely live-executed against the live database and a live Salesforce query.

The live CRM integration is written to degrade gracefully by design: no client module, no credentials, or a live API error all fall through to "digest produced, CRM section omitted or shows the error verbatim," never a hard failure or a silently suppressed section.

Real, live-executed run

Lifecycle Pulse: a real digest

.claude/skills/lifecycle-pulse/digest_output/2026-09-05-digest.md

The one genuinely live-executed digest, run against the real database on 2026-09-05: funnel counts by segment across all six stages, plus a data-quality note citing 89 lifecycle-stage mismatches across 92 matched cross-system contacts. Its live CRM snapshot section shows a real, left-in-not-suppressed authentication failure from an actual Salesforce API call attempted during that run, a deliberate choice: a digest that goes quiet on a broken integration is judged worse than one that states the failure plainly.
