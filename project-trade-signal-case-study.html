Fireclay Case Study

A live lifecycle-analytics system built to show, not describe, what this role's job description asks for: a friction point diagnosed from real data, two live CRMs reconciled against each other with a scoped fix, a reactivation mechanism tested and fixed against the live system it depends on, and a reusable Claude Code skill that keeps the analysis running instead of living in a one-time export.

The finding that started it

From a 3,200-customer synthetic dataset modeled on Fireclay's own funnel language (interest → sample → project → purchase → repeat → advocacy), analyzed directly with Claude Code against a local SQLite store.

73%

of trade leads acquired at trade shows who request exactly one sample never advance to a project upload or purchase — more than double the stall rate of leads acquired through email capture (33%). The single strongest predictor of eventual purchase in this segment is requesting a second sample, which trade-show leads do at less than half the rate of the trade segment overall.

HubSpot ↔ Salesforce reconciliation

A live, config-driven reconciliation of both real accounts — not a mockup of one. The methodology is generic (the matching engine has no Fireclay-specific field names); the findings below are from actually running it.

Finding

100% lifecycle-stage disagreement

Of 85 contacts genuinely live in both systems, all 85 show HubSpot's lifecyclestage stuck at "lead" while Salesforce's Lead.Status already reads "Closed - Converted" — one mechanism (a field never written to after import), not scattered noise. A fuzzy name-matching fallback also produced 7 false positives out of ~400 tries, found and reported rather than hidden.

Systems memo

What would actually fix it

A scoped recommendation grounded in the real data: one Salesforce Flow (fire on Lead.Status change) plus one HubSpot API call, one direction only — not a platform purchase. Answers the JD's own "systems requirements" phrase directly.

Experimentation: a real stop-and-redesign decision

Real analysis against real historical volume, not a simulated experiment result. The question asked before spending any runway: can the backlog's own proposed test actually work?

Finding

The test as specified can't work

A power analysis shows the backlog's proposed test (90-day holdout, 8pp scale threshold) needs 623 trade-show leads. The channel produces ~10/month — 62 months to get there. Checked whether a faster-arriving proxy metric would fix it; it doesn't, confirming a real population ceiling, not a fixable test design.

Decision

Stop, learn, redesign

Kills the randomized-holdout design, not the hypothesis: full rollout to all eligible trade-show leads, directional monitoring over two quarters against the 11% baseline, and an explicit reversal bar (pull back if the rate isn't at least 5pp above baseline) — the JD's own "scale, stop, or learn next" language, answered with an actual call.

Reactivation: the mechanism, made real

The JD names "activation, education, nurture, reactivation" as the lifecycle side of the Trade Program. This backlog hypothesis (a Trade Portal single-sample re-entry flow, the Sample Kit Builder below) couldn't be evaluated for a real conversion rate — no production traffic yet. So this round tested whether the mechanism itself actually works against the live store, and it didn't, until a real bug was found and fixed.

Live systems check

A bug only a live test would catch

The three companion sample products backing the Sample Kit Builder had zero real inventory with a deny-oversell policy — the reactivation prompt would have failed silently the moment a real lead clicked it, with no error anywhere a merchandising owner would notice.

Fixed, live + in code

From console.log stub to a real cart action

Restocked all three SKUs live (verified via each API call's response, not assumed) and rebuilt the button's handler to resolve real variant IDs in Liquid and POST an actual /cart/add.js call, with honest success/error states in place of the old stub. Written and committed; not yet pushed to the live preview theme below.

Lifecycle Pulse

A real, git-committed Claude Code skill — not a described one. Anyone who clones the working repo and opens Claude Code inside it gets it auto-discovered and runnable.

Claude Code skill

Lifecycle Pulse funnel digest

Generates a week-over-week lifecycle/funnel digest — interest, sample, project, purchase, repeat, advocacy — by segment, with anomaly flags where a stage's count drops past a configurable threshold, plus a live HubSpot/Salesforce cross-reference. Three snapshots are backdated re-derivations of real data (simulated cadence, real counts); one digest is a genuinely live-executed run pulling real numbers from both the local funnel database and the live Salesforce org.
